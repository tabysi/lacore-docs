# Discord & Duty — `configs/cfg-server-sv.lua`

Server-only config (never sent to clients). Handles dev mode, the built-in Discord role
authentication, the on-duty whitelist, and the webhook log channels.

## Dev mode

```lua
devmode = GetConvar("lacore_devmode", "false") == "true"
```

See the [`lacore_devmode` convar](/configuration/convars#dev-mode). When on, it disables webhooks,
bypasses **all** connect checks, and grants every player full staff/dev permissions. Never on in
production.

## External chat

```lua
ExternalChat = false
```

LACORE ships a lightweight OOC chat: it takes over the stock `chat` message, re-posts it as
"OOC | Name", logs it to Discord and runs a name anti-spoof + slur filter. If you run a
**third-party chat resource** (cc-chat / cc-rpchat, …), every line shows twice and their RP names
can trip the anti-spoof kick — set `ExternalChat = true` so the other chat owns the display. The
Discord OOC log and the slur filter stay active.

## Entity lockdown (anti-cheat vs. NPC traffic)

```lua
EntityLockdown = "strict"
```

LACORE locks the default routing bucket so clients can't spawn arbitrary networked entities — a
common cheat/griefing vector. The catch: ambient NPC traffic and pedestrians are **also**
client-spawned, so a locked bucket means empty streets.

| Value | Behaviour |
| --- | --- |
| `"strict"` *(default)* | Max protection, but **no** ambient NPC traffic / peds. |
| `"inactive"` | Vanilla: NPC traffic + peds come back, but clients may spawn any entity again (other anti-cheat checks still run). |
| `"relaxed"` | Middle ground; may or may not restore ambient traffic — test it on your build. |

Want NPC cars back? Set `"inactive"`.

## Access control (whitelist & Discord on/off)

Framework servers (ESX / QBCore / QBox) usually handle identity and permissions themselves and don't
need LACORE's Discord layer or its members-only whitelist. Switch either off here:

```lua
AccessControl = {
    whitelist    = true,    -- members-only join gate (/wl). false = disabled entirely.
    discordRoles = true,    -- require + read Discord roles and bridge them to ACE. false = off.
    membership   = "auto",  -- who counts as a "member" for member-only perks. See below.
}
```

| Toggle | `false` means |
| --- | --- |
| `whitelist` | The members-only gate is off: `/wl` does nothing and no one is ever rejected with “members only”. **Bans and the global-ban network still apply.** |
| `discordRoles` | LACORE no longer requires Discord at connect (no “join our Discord” rejection), doesn't read Discord roles, and doesn't bridge them to ACE. Duty-role gating (`DutyRoles`) is skipped, and Staff/Dev powers come from **ACE / txAdmin** only. |

### Membership (member-only perks)

`membership` decides who counts as a **member** for member-only perks — going on agency duty (`/onduty`),
spawning member vehicles, and voting on the community board. This is separate from the join whitelist;
membership normally rides on the Discord **“Member”** role.

| Value | Behaviour |
| --- | --- |
| `"auto"` *(default)* | With Discord role auth **on**, a member is anyone holding the Discord “Member” role. With Discord auth **off** there is no role to read, so **everyone is a member**. |
| `"open"` | Everyone is always a member, even with Discord auth on. |
| `"role"` | Always require the Discord “Member” role — locks the perks for everyone when Discord auth is off, so only use it with Discord on. |

<Callout type="info">
  On an ESX / QBCore / plug-and-play server (`discordRoles = false`), `"auto"` is what makes `/onduty`
  and the other member-only perks **just work** — otherwise, with no “Member” role to read, they would be
  silently locked for everyone. Duty is still authorised by the framework job (see the
  [Framework Bridge](/features/bridge)); `membership` only governs LACORE's own member gate.
</Callout>

<Callout type="info">
  **Plug-and-play:** even with `discordRoles = true`, Discord is only *enforced* once it's actually
  configured (a bot token **and** guild id are set). On a fresh install with no token, Discord stays
  **idle** — players connect without it and no roles are read — and the moment you set the convars, role
  features light up. So you never have to touch this to get the core running.
</Callout>

<Callout type="warning">
  With `discordRoles = false` (or while Discord is idle), admin powers don't come from Discord — grant
  them through ACE (e.g. `add_ace group.admin lacore allow` in `server.cfg`) or txAdmin, and duty
  authorisation comes from the framework job (see the [Framework Bridge](/features/bridge)).
</Callout>

## Discord role authentication (built-in)

LACORE reads Discord roles directly via a bot token (no external `discordroles` resource). Roles are
cached per player and exposed via `GetDiscordRoles()` / `IsDiscordRolePresent()`.

```lua
DiscordAuth = {
    token        = GetConvar("lacore_discord_token", ""),
    guild        = GetConvar("lacore_discord_guild", ""),
    cacheSeconds = 300,   -- how long fetched roles are cached

    -- Map role NAMES (used in code) → your Discord role IDs.
    -- Enable Developer Mode in Discord, right-click a role → Copy Role ID.
    roles = {
        Member        = "1271895547485356203",
        Staff         = "1234427956432994321",
        Dev           = "1280438326582837278",
        LeadDeveloper = "1395534398299832431",
        LOA           = "1310081058762653696",
        LE            = "1285460493619953720",
        -- Supporter / Donator tiers … (leave empty = "never present")
    },
}
```

<Callout type="info">
  The bot must be **in your guild** and have the **Server Members Intent** enabled (Developer Portal
  → Bot → Privileged Gateway Intents). Leave a role ID empty to treat it as never present.
</Callout>

Role names referenced elsewhere (profile badges, Big Brother access, duty whitelist) must match keys
in this `roles` table.

## Duty whitelist

Closes the gap where any client could self-assign a duty job. Checked server-side in `ondutyServer`.

```lua
DutyRoles = {
    ["Law Enforcement"] = "LE",  -- requires the LE role
    ["Fire/EMS"]        = "",    -- open by default
    ["Coroner"]         = "",    -- open by default
}
```

- `devmode` and `Staff` / `Dev` bypass the check.
- An empty value (`""`) means no restriction — anyone may take that job.
- Values are role names from `DiscordAuth.roles`.

## Web dispatcher access

Who may use the [hosted web dispatcher](/features/webdispatch) for **your** server:

```lua
WebDispatchAccess = {
    dispatch = {},  -- e.g. { "Staff", "Dispatch" } — may act: status, assign, create, close
    view     = {},  -- e.g. { "Member" }            — may watch, cannot act
}
```

**Both lists empty = nobody but you** — that is the default on purpose. You (the license-key owner)
and your dashboard team always have access without appearing here. Role **names** come from
`DiscordAuth.roles`; the check runs on your server with your own bot token — the website only asks
"may this Discord id dispatch?" and gets yes/no/read-only back.

## Agency whitelist

`DutyRoles` above gates the **job** ("Law Enforcement"). `DutyAccess` in `configs/cfg-server-sv.lua`
gates the **agency** — the `short` of an entry in `configs/config.lua` `agencies` (`LAPD`, `LASD`,
`CHP`, …). That matters because the agency is what decides the MDT portal a unit gets:

| Agency (department) | Portal `/mdt` opens |
| --- | --- |
| `LAPD` | LAPD Mobile Client |
| contains `LASD` / `Sheriff` / `BCSO` | LASD CAD/PCMS |
| any other law-enforcement agency | Agency MDT (CHP style) |
| Fire / EMS / Coroner | EMS CAD |

A player who may not take an agency never gets its department — and without the department, `/mdt`
never opens that agency's portal. There is no separate "portal permission" to keep in sync.

An agency can require a **Discord role**, an **ACE permission**, or both. Holding **either one** is
enough — they are alternatives, so you can move a department from one to the other without a flag day.

```lua
DutyAccess = {
    enabled     = true,      -- ships false (no agency gate); set true to turn it on
    bypassStaff = true,      -- let Staff/Dev take any agency; false = strict

    agencies = {
        LAPD = { role = "LAPD" },                           -- Discord role only
        LASD = { ace  = "lacore.duty.lasd" },               -- ACE only
        CHP  = { role = "CHP", ace = "lacore.duty.chp" },   -- either one is enough
        NPS  = { role = { "NPS", "1285460493619953720" } }, -- several roles / raw role id
        SAHP = "lacore.duty.sahp",                          -- short form for { ace = … }
    },

    fallback = "allow",      -- agencies with no entry: "allow" (default) or "deny"
}
```

`role` and `ace` each take one string or a list, and any single entry in that list is enough.

### Option A — Discord roles

`role` is a key from the `DiscordAuth.roles` table above, the same place `DutyRoles` reads from. Add
your department roles there and point the agency at them:

```lua
DiscordAuth = {
    roles = {
        LAPD = "1285460493619953721",
        CHP  = "1285460493619953722",
    },
}
```

Nothing else to set up — no `server.cfg` lines, no ACE groups. A raw Discord role id also works
directly as a `role` value if you would rather not register it.

### Option B — ACE (vMenu-style servers)

If your server already maps Discord roles to ACE groups — the usual vMenu setup — keep the principals
you have and grant each one the LACORE ace once in `server.cfg`:

```cfg
add_ace group.lapd lacore.duty.lapd allow
add_ace group.lasd lacore.duty.lasd allow
add_ace group.chp  lacore.duty.chp  allow
```

<Callout type="info">
  ACE checks ask about **ace objects**, not about groups, so `group.lapd` on its own is not something
  LACORE can test for. The `add_ace` line above is what connects your existing group to the permission
  LACORE asks about. Any resource that puts players into ACE groups works — vMenu's own role mapping,
  a Discord→ACE bridge, or plain `add_principal` lines in your `server.cfg`.
</Callout>

### Behaviour

- Checked **server-side** in `ondutyServer`, so a client cannot bypass it.
- Not waived by the ESX/QBCore framework bridge: on a server that gates agencies, the gate is the last
  word.
- `devmode` bypasses everything, as everywhere else.
- Civilian `/job` names are never gated — a strict `fallback = "deny"` cannot lock a mechanic out of
  their own job.
- Keys are matched case-insensitively, so `CHP` and `chp` behave the same.
- A **role-only** agency on a server whose Discord auth is off or idle cannot be answered either way,
  so it falls back to your `fallback` value and logs one line to the console — rather than silently
  refusing everyone for a reason nobody can see. Agencies with an `ace` are unaffected.

<Callout type="info">
  A refused `/onduty` puts the player back to civilian and takes back the loadout that agency handed
  out (only those weapons), then logs the missing role/ACE to the server console and your admin
  webhook.
</Callout>

### Checking it works

`/dutyaccess` prints the caller's agency access — a `+`/`-` per configured agency plus what each one
wants. Run it in-game as the player you are testing, or in the server console.

```
LACORE  Agency access (DutyAccess) — + allowed, - denied:
  + CHP   [role CHP or ace lacore.duty.chp]
  - LAPD  [role LAPD]
  - LASD  [ace lacore.duty.lasd]
```

## Vehicle spawner permission

The `/vehicle` spawner menu is open to everyone by default. Gate it behind an ACE permission:

```lua
VehicleSpawner = {
    permission = "",   -- "" = everyone; e.g. "vehiclespawner" = requires the ACE below
}
```

```cfg
add_ace group.admin lacore.vehiclespawner allow
```

Checked server-side via the shared `HasPermission` helper — `devmode` and Staff/Dev always pass.
This gates LACORE's spawner menu, not entity creation as such (that is the anticheat's job).

## Webhooks

Webhook URLs are read from convars so they never live in the code. Any left empty disables that
channel.

```lua
Webhooks = {
    ServerLog       = GetConvar("lacore_webhook_serverlog", ""),
    FiveMLiveChat   = GetConvar("lacore_webhook_livechat", ""),
    AdminLog        = GetConvar("lacore_webhook_adminlog", ""),
    DispatchLog     = GetConvar("lacore_webhook_dispatch", ""),
    UserReports     = GetConvar("lacore_webhook_reports", ""),
    BugReport       = GetConvar("lacore_webhook_bugreport", ""),  -- your own copy of /lacorereport reports
    PrisonLog       = GetConvar("lacore_webhook_prison", ""),
    BleeterLog      = GetConvar("lacore_webhook_bleeter", ""),
    txAdminAdminLog = GetConvar("lacore_webhook_txadmin", ""),
}
```

Set the matching convars in `server.cfg` — see [Server Convars](/configuration/convars#discord-webhooks).

## Discord Rich Presence — `configs/cfg-presence-sh.lua`

Shows a live status on each player's Discord profile with clickable buttons, so their friends can see the
server and join. Set the fields directly in the config — a plain `set` convar is server-only and can't
reach the client, so presence is **not** driven by convars.

```lua
RichPresence = {
    enabled    = true,
    appId      = 0,              -- Discord Application ID (number); 0 = disabled
    largeAsset = "icon",         -- art asset key uploaded in the Dev Portal
    smallAsset = "",
    discordInvite = "discord.gg/YOURINVITE",   -- "Discord" button
    website       = "",                        -- "Website" button (blank = hidden)
    lines = {                    -- status text; {players} / {aop} / {discord} are filled live
        "{players} Players | AOP: {aop}",
        "{players} Players | {discord}",
    },
    rotateSeconds = 4,           -- seconds between rotating through the lines above
    connectCard   = false,       -- true = a "Join Discord" card on the connect screen; false = instant connect
}
```
