# Supervisor Panel

A rank-gated oversight tablet for **shift supervisors and watch commanders**. It bundles what LACORE
already knows — units, incidents, BOLOs, warrants, the map — into one screen, and adds the few command
actions a supervisor actually needs during a shift.

Open it with **`/supervisor`** (configurable). **Escape** closes it.

<Callout type="info">
  A supervisor no longer has to be registered as a **dispatcher** to direct their shift. The panel
  reuses the dispatch backend, and the server authorises a verified supervisor for those actions while
  the panel is open.
</Callout>

## Who can open it

Access is **decided by the server**, never by the client. There are **four** ways to qualify, and they
are checked independently — **any single one is enough**:

<Steps>

### ACE permission

The unit is allowed the configured ACE object (`ace`, or `aceByDept`). Grant it to a *group* once and
every member inherits it — no identifiers to collect per person.

### Discord role

The unit holds one of the roles named in `roles` (or `rolesByDept`). Needs a bot token; the roles
themselves *are* the permission, so nothing goes into `server.cfg` at all.

### Config allowlist

The unit's **license identifier** or **exact callsign** is listed in `allow`. This is the standalone
path — it works with no framework at all, and it's also how you grant the panel to specific people
regardless of their grade.

### Framework job grade

On an ESX / QBCore / QBox server the unit's **job grade** is compared against a minimum
(`minGrade`, with an optional per-department override). This is the natural path if your ranks already
live in the framework.

</Steps>

Before any of them, `leoOnly` applies: with its default `true` a civilian is never a supervisor, no
matter what else checks out.

<Callout type="warning">
  **The four paths are OR, not AND.** Adding a Discord role does not *replace* the other checks — it
  adds one more way in. On a framework server `minGrade` defaults to **3**, so every unit at grade 3
  or above keeps the panel whatever their Discord roles say. To gate on one path alone, switch the
  others off — see [Only Discord roles, nothing else](#only-discord-roles-nothing-else).
</Callout>

<Callout type="warning">
  On a **standalone** server there is no job grade, so every grade is `0` and the grade check never
  passes. You must fill the `allow` list — otherwise nobody can open the panel.
</Callout>

## Configuration

Everything lives in `configs/cfg-supervisor-sh.lua`.

| Key | Default | What it does |
| --- | --- | --- |
| `command` | `"supervisor"` | The chat command that opens the panel. |
| `minGrade` | `3` | Minimum framework job grade that counts as a supervisor. |
| `minGradeByDept` | *(empty)* | Per-department override, e.g. `["LSPD"] = 4`. Falls back to `minGrade`. |
| `ace` | `"lacore.supervisor"` | ACE object that grants the panel. `false` or `""` switches the ACE path off. |
| `aceByDept` | *(empty)* | Per-department ACE object, e.g. `["LSPD"] = "lacore.supervisor.lspd"`. Checked before `ace`. |
| `roles` | *(empty)* | Discord role **names** from `DiscordAuth.roles`. Holding any of them grants the panel. |
| `rolesByDept` | *(empty)* | Per-department role list, e.g. `["LSPD"] = { "LAPDSupervisor" }`. Checked in addition to `roles`. |
| `allow` | *(empty)* | Allowlist keyed by **license identifier** (`license:…`) **or exact callsign** (`"1-L-30"`), value `true`. |
| `leoOnly` | `true` | Only on-duty LEO units are ever eligible. Set `false` to allow any job that clears the checks. |

```lua filename="configs/cfg-supervisor-sh.lua"
SupervisorConfig = {
    command = "supervisor",

    minGrade = 3,
    minGradeByDept = {
        ["LSPD"] = 4,
    },

    ace = "lacore.supervisor",
    aceByDept = {
        ["LSPD"] = "lacore.supervisor.lspd",
    },

    roles = { "LAPDSupervisor", "BCSOSupervisor", "SAHPSupervisor" },
    rolesByDept = {
        ["LSPD"] = { "LAPDSupervisor" },
    },

    allow = {
        ["license:0000000000000000000000000000000000000000"] = true,
        ["1-L-30"] = true,
    },

    leoOnly = true,
}
```

### Granting the panel with ACE

With more than a handful of supervisors, the ACE path is the one to use: allow the object on a
**group** once, then add people to that group. Nobody's license identifier has to be collected, and
unlike a callsign an ACE cannot be typed by someone else.

```cfg filename="server.cfg"
# one group per department
add_ace group.lapd_supervisor lacore.supervisor allow
add_ace group.bcso_supervisor lacore.supervisor allow
add_ace group.sahp_supervisor lacore.supervisor allow

# members inherit it — any identifier works (discord:, license:, fivem:, steam:)
add_principal identifier.discord:123456789012345678 group.lapd_supervisor
add_principal identifier.license:0000000000000000000000000000000000000000 group.bcso_supervisor
```

Because ACE objects are hierarchical, `add_ace group.watch_command lacore allow` grants
`lacore.supervisor` along with every other `lacore.*` right — which is also why `group.lacore_dev`
already has the panel.

Running a **Discord→ACE bridge**? Map your supervisor roles to those groups there instead and the
membership keeps itself in sync — a role change in Discord is all it takes, with nothing to edit in
`server.cfg`.

Want each department gated separately, give them their own object with `aceByDept`:

```cfg filename="server.cfg"
add_ace group.lapd_supervisor lacore.supervisor.lspd allow
```

<Callout type="info">
`leoOnly` still applies: an ACE holder must be an on-duty LEO unit to open the panel. Check who the
server thinks you are with **`/myperms`** — it reports `supervisor=true|false`.
</Callout>

### How-to: gate the panel on a Discord role

The roles can **be** the permission — nothing goes into `server.cfg`, and handing out or taking away
the panel is a role change in Discord. Four steps.

<Steps>

### Check the prerequisites

The role path needs a Discord bot. Set both convars in your `server.cfg`:

```cfg filename="server.cfg"
set lacore_discord_token "YOUR_BOT_TOKEN"
set lacore_discord_guild "YOUR_GUILD_ID"
```

The bot must be **a member of your guild** and have **Server Members Intent** enabled
(Discord Developer Portal ▸ your app ▸ Bot ▸ Privileged Gateway Intents). Without the intent Discord
returns no member data, the role check silently never matches, and you are left wondering why the
panel does not open. `/lacore doctor` reports whether the token and guild are set.

### Name your roles

Copy each role's ID in Discord (right-click the role ▸ **Copy Role ID**; Developer Mode must be on in
Discord ▸ Settings ▸ Advanced) and add it to `DiscordAuth.roles` under a name of your choosing. That
name is what the rest of LACORE refers to:

```lua filename="configs/cfg-server-sv.lua"
DiscordAuth = {
    roles = {
        -- … your existing roles …
        LAPDSupervisor = "1234567890123456789",
        BCSOSupervisor = "2345678901234567890",
    },
}
```

### Make those roles supervisors

List the **names** — not the IDs — in `roles`:

```lua filename="configs/cfg-supervisor-sh.lua"
roles = { "LAPDSupervisor", "BCSOSupervisor" },
```

Should a role only count for units of one department, use `rolesByDept` instead (or as well — both
lists are checked):

```lua filename="configs/cfg-supervisor-sh.lua"
rolesByDept = {
    ["LAPD"] = { "LAPDSupervisor" },
    ["BCSO"] = { "BCSOSupervisor" },
},
```

The key is the department's `short` from `configs/cfg-agencies-sh.lua`.

### Restart and verify

Restart the resource, go on duty as a LEO unit and run **`/myperms`** — it prints
`supervisor=true|false`, which is the same server-side answer the panel gate uses. `true` means
`/supervisor` will open.

</Steps>

<Callout type="warning">
Roles are cached for `DiscordAuth.cacheSeconds` (**5 minutes** by default). A role you just granted
can take that long to reach a player who is already connected — a reconnect applies it immediately.
</Callout>

### Only Discord roles, nothing else

Adding roles does **not** turn the other paths off. This matters most on a framework server: `minGrade`
defaults to `3`, so every unit at grade 3+ keeps the panel regardless of their Discord roles. If the
role is supposed to be the *only* thing that decides, close the other three doors:

```lua filename="configs/cfg-supervisor-sh.lua"
roles    = { "LAPDSupervisor", "BCSOSupervisor" },
minGrade = 999,     -- no job grade ever reaches this → framework path off
ace      = false,   -- ACE path off (leaving it unset means the default lacore.supervisor applies)
allow    = {},      -- no manual entries
```

<Callout type="info">
  **Consider keeping `ace`.** It is your way back in when Discord is unreachable or the bot token
  expires — `group.lacore_dev` inherits `lacore.supervisor` through its blanket `lacore` ACE, so an
  owner can still open the panel. If you would rather keep that safety net, leave `ace` alone and only
  raise `minGrade`; that already removes the path that hands the panel out in bulk.
</Callout>

### It doesn't work — what to check

| Symptom | Likely cause |
| --- | --- |
| `/supervisor` does nothing, `/myperms` says `supervisor=false` | Role not in `DiscordAuth.roles`, a typo between the two files (the name must match exactly, case-sensitive), or an empty role ID. |
| Nobody gets the panel, no matter the role | Missing bot token/guild, or **Server Members Intent** off. Every role check then answers "no". |
| The role was just granted and still nothing | The 5-minute role cache. Reconnect, or wait it out. |
| Someone has the panel who should not | Another path is letting them in — most likely `minGrade` (default 3), or an inherited ACE. See above. |
| A role holder who is off duty or civilian can't open it | Working as intended: `leoOnly` requires an on-duty LEO unit. |

### Which path should I use?

| Situation | Use |
| --- | --- |
| Departments are managed in Discord, no bridge in place | **Discord role** — `roles` |
| You already run a Discord→ACE bridge | **ACE** — map the role to a group, allow `lacore.supervisor` on it |
| ESX / QBCore / QBox with real job grades | **Grade** — `minGrade` / `minGradeByDept` |
| A handful of people, no framework, no bot | **Allowlist** — `allow` with license identifiers |

The paths are checked independently and any one of them is enough, so mixing them is fine — a
framework server can still hand the panel to one guest supervisor by ACE.

### Personnel & cases

Two more config files come with the records modules:

| File | What it holds |
| --- | --- |
| `configs/cfg-personnel-sh.lua` | The **write bar** (`writePermission`, `writeMinGrade`) plus the vocabulary: entry types, personnel statuses, and the certifications your departments issue. |
| `configs/cfg-cases-sh.lua` | The case-number **agency prefix** (`LAPD-26-000142`), case types, narrative sections, person/vehicle roles and dispositions. |

Both are read by the terminal at open time, so renaming a certification or adding a case type takes effect
without touching the UI.

## The terminal

It is laid out like a records application, not a game menu: a **module rail** on the left, **several
records open at once as tabs** along the top, dense sortable grids, labelled field sheets, a
function-key bar (`F2` search, `F5` refresh, `ESC` close) and a status line. Three themes —
**classic** (light, the realistic look), **dark** and **amber** — switchable from the ⚙ menu, along
with opacity and scale. The window is draggable and remembers where you put it.

## Modules

### Watch

The shift at a glance, in four views:

- **Roster** — every on-duty unit: **status** (colour-coded), **callsign**, **rank**, **name +
  department**, the **incident** they're attached to and their **location**. Sortable and searchable;
  supervisors carry a **★**, the job grade shows as `G<n>`, and partners sharing a callsign merge into
  one row. Selecting a unit opens its detail sheet.
- **Map** — every unit and active incident on the LACORE map, same projection and tiles as the
  [dispatch console](/user-guide/dispatch-console).
- **Dispatch** — pick a unit and an incident to **assign** (the unit goes *enroute* and is attached), or
  set its **status** directly.
- **Broadcast** — a division-wide message to all units plus the **attention tone**, with the recent radio
  traffic underneath.

### Warrants & BOLO

Active **BOLOs** with one-click cancel, and **every character currently carrying a warrant**. Warrants
themselves are set and cleared from a person's record in any CAD — see
[BOLO](/user-guide/bolo) and [Citations & Charges](/user-guide/citations-charges).

### Personnel

An officer's service record. The index lists everyone the server has seen on duty; opening one gives:

| Tab | Contents |
| --- | --- |
| Identity | Name, callsign, department, rank, status, first/last seen |
| Service | Total time on duty (broken down per department), playtime, and the **shift log** |
| Training & Certs | Certifications held, and when they were issued |
| Discipline & Commendations | Commendations, reprimands, counseling, training notes |
| Activity | Arrests, citations, warnings, reports and evidence authored by this officer, the dispatch calls they closed, and every charge broken down into Infraction / Misdemeanor / Felony. The officer sees the same figures for themselves in [My Activity](/user-guide/officer-stats). |
| History | Callsign history and rank history |

**Reading** a file needs the supervisor rank. **Writing** one is a higher bar — see
[Editing personnel files](#editing-personnel-files).

<Callout type="info">
  Nothing from before this feature existed can be attributed — there was no rank, no duty history and no
  author stored on older records. Files start when the officer was first seen, and the Activity tab states
  the date its counters begin from rather than implying they cover the server's whole history.
</Callout>

### Cases

The extended report layer. A case ties an incident, the people and vehicles involved, the reports already
on their records and a multi-section **narrative** into one numbered file — `LAPD-26-000142`, from its own
counter, deliberately **not** the incident number (that one rolls over and is reused).

A case is a **container, not a copy**: reports keep living on the person's record and the case points at
them. File a report the normal way with a case number and it links both ways.

Tabs: **Summary** (with incidents, disposition and submit), **Narrative**, **Persons**, **Vehicles**,
**Reports**, **Audit**.

### Review queue

Submitted cases waiting for a decision, **oldest first**, with a badge showing how many. A supervisor
approves or rejects; **a rejection requires a reason** (enforced on the server, not just greyed out) and
the submitting officer is notified either way.

Approving **locks** the case. Corrections open a **supplement** — a new case carrying the parent's number
— so a signed-off file is never quietly rewritten.

### Master index

Search a person or a plate and see everywhere it turns up: their own record (warrants, arrests, citations,
reports, evidence), their registered vehicles, and every case they appear on — as suspect, victim, witness
or officer of record. Clicking a result opens that case as its own tab.

## Editing personnel files

Promotions, certifications and discipline are career records, so writing them is deliberately a **second,
higher bar** than reading them. A writer qualifies with **either**:

1. the **`lacore.personnel.write` ACE permission** (also satisfied by staff/dev and by devmode), or
2. a **job grade** at or above `PersonnelConfig.writeMinGrade`.

Both are checked on the server and re-checked on every write. Without it the file stays fully readable and
says so. Reads are audited too, and a file containing discipline entries is logged as such.

## Server authority & audit

- The client only **asks** to open; the server verifies the rank and grants it.
- The panel's actions are authorised server-side for a verified supervisor **with the panel open** — so
  closing the panel ends the elevated access.
- The warrant list is a **supervisor-only** lookup and returns names and reasons only.
- Warrant changes made from a CAD are written to the **BigBrother audit**, and fire
  `lacore:api:warrantChanged` for integrations.

<Callout type="info">
  LACORE had no rank field before this panel. On-duty units now carry a `grade` (read from the
  framework bridge where available), and it is included in the unit roster — which is what the ★ and
  `G<n>` in the roster come from.
</Callout>

## Troubleshooting

| Symptom | Cause |
| --- | --- |
| `/supervisor` says you're not a supervisor | None of the four paths matched. On standalone servers the grade is always `0` — use the ACE or Discord-role path. Run `/myperms` to see what the server thinks. |
| The Discord role is there but the panel is not | No bot token / guild id set, the role is missing from `DiscordAuth.roles`, or the 5-minute role cache hasn't caught up yet. |
| You want to test it without setting ranks up | Enable **devmode** (`setr lacore_devmode "true"`) — it opens the gate for everyone, exactly like the dispatch and officer checks. Never leave it on in production. |
| Nobody can open it | Standalone server with an empty `allow` list. |
| A supervisor can't assign or set status | They opened the panel, then it was closed — the elevated access only lasts while it is open. |
| The map is blank | Same tile setup as the dispatch console; check your map tiles resource. |
| The roster is empty | Nobody is on duty with a callsign — the roster is built from on-duty units. |
