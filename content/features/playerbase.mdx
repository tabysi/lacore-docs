# Enhanced Playerbase <span style={{fontSize:'0.6em',verticalAlign:'middle',opacity:0.7}}>BETA</span>

The **Enhanced Playerbase** turns your local bans and warns into a shared, cross-community reputation
layer. Upload your records to the LACORE playerbase, share them with partner communities by a key, and
— if you choose — **enforce** partner bans automatically when a player connects.

![The shared playerbase — hashed records, share keys and two-sided enforcement](/img/features/playerbase.svg)

<Callout type="info">
  The playerbase is **advisory by default**. Nothing auto-bans anyone until you deliberately turn on
  enforcement on *both* sides. Uploading and sharing only ever expose **hashed** identifiers.
</Callout>

## How it works

- **Records** — every ban and warn keeps its provenance (which community, which server, who issued it).
- **Players** — records attach to a shared *player*, matched across servers by **hashed identifiers**
  (SHA-256, no per-server salt) so the same person lines up everywhere without exposing raw identifiers.
- **Ghosts** — if you ban someone the playerbase has never seen, a **ghost** player is minted to hold
  the record. The next time that person connects to a participating server, the ghost is **claimed**
  (their real identifiers attach, the ghost flag drops).

## 1 · Upload your records

Local bans and warns live in `data/banlist.json` (warns carry `type="Warning"`). Share them from the
server console:

```
/lacore bans list     # count your local bans + warns
/lacore bans upload    # push them to the LACORE playerbase
```

Upload rides the write-only relay and your **license key** — no key, nothing is sent. Server-side the
records are hashed, deduped and attached to a shared player (a ghost if unknown).

<Callout type="info">
  Requires a [license key](/customer-portal/license-keys) (`setr lacore_license_key "…"`). Duplicate
  records (same local id from the same community, or same player + reason) are skipped automatically.
</Callout>

### If you ban from txAdmin

Most teams do — and txAdmin keeps its **own** database. `data/banlist.json` only ever held bans issued
with LACORE's `/ban` and `/warn`, so a txAdmin server would upload a handful of records while hundreds
stayed behind.

**You do not have to do anything.** On every start LACORE looks for txAdmin's `playersDB.json` beside
your server and carries over what it finds — bans, warns, the lot. It runs at each boot rather than
once, which also covers bans issued in the panel while your server was down: those fire no event, so
without the sync they would never arrive.

Carrying over is safe to repeat. Records keep txAdmin's own action id, so a second pass adds nothing,
and bans an admin already lifted or that have run out are skipped rather than resurrected. The console
stays quiet unless something actually came across.

**New bans arrive as they happen.** `Integrations.txAdminBans` in `configs/cfg-integrations-sh.lua`
ships as `"auto"`, which mirrors every new txAdmin ban and warn the moment it is issued. Set it to
`false` to switch off both the mirroring and the boot sync.

<Callout type="info">
  Run `/lacore bans import` to do it on demand and see exactly what happened — which file was found,
  how many actions it holds, and what was skipped and why. In the **server console** (including
  txAdmin's live console) type it without the leading slash: `lacore bans import`.
</Callout>

#### Where it looks

A configured data path first, then txAdmin's own; then the artifacts folder, which is where txAdmin
puts `txData` by default; and finally the folders above the resource — plus the ones **beside** them.
That last part covers the common Linux split where the artifacts and the resources sit in separate
trees (`/home/FXServer/server` next to `/home/FXServer/server-data`), because walking straight up from
a resource in the second one never passes a `txData` at all.

**If it cannot find the file**, the command says how many paths it tried and lists the folders it
searched. Two things can put you here, and the list tells them apart: a layout nobody guessed (one line
will be your own path, off by a folder), or an FXServer build that gives resources no file access
outside their own folder — which the command names explicitly.

Point LACORE straight at it in `server.cfg`:

```cfg
setr lacore_txdata_path "/home/FXServer/server/txData"
```

That is the `txData` folder itself — the one holding `<profile>/data/`. The full path to
`playersDB.json` works too. `Integrations.txAdminDataPath` in `configs/cfg-integrations-sh.lua` does
the same; the convar wins if both are set. Restart the resource afterwards.

If file access is blocked outright, copy `txData/<profile>/data/playersDB.json` into the resource as
`data/txadmin-import.json` instead and run `/lacore bans import` — the command prints the exact path to
copy it to. Live mirroring is unaffected either way; it never touches the filesystem.

<Callout type="warning">
  txAdmin keeps **one database per profile**. If the sync reports *0 actions* while your panel shows
  bans, it found a different profile than the one your panel is looking at — a leftover dev profile on
  the same machine looks identical from the outside.
</Callout>

<Callout type="info">
  Mirroring is **local bookkeeping** — nothing leaves your server. Sharing is still the deliberate
  `/lacore bans upload`.
</Callout>

## 2 · Share with partner communities

In the dashboard under **Community → Players → Bans/Warns Database** you generate a **share key**
(`PBSHARE-XXXXX-XXXXX-XXXXX`). Hand it to a partner and they paste it to pull your records into their
list, tagged with your name. See [Players & sharing](/customer-portal/players) for the dashboard flow.

Sharing is **directional** (giving a partner your key lets *them* read *you*, not the reverse) and
**revocable** (revoke the key to cut every subscriber at once).

## 3 · Enforcement (opt-in, two-sided)

Enforcement makes a server actually **reject** a connecting player who carries an active ban in its
playerbase. It requires agreement from **both** sides:

<Steps>

### Owner marks the key "Enforce"

On the sharing side, flip your key's scope from **Read only** to **Enforce**. This permits partners to
auto-reject players *you* banned. Plain read grants stay advisory.

### Consuming server enables the convar

The server that wants to enforce sets:

```cfg
setr lacore_playerbase_enforce true
```

</Steps>

Only when the owner grants **Enforce** *and* the consuming server enables the convar does a shared ban
block a connect. A server always enforces **its own** bans when the convar is on; partner bans are
enforced only for partners who granted the Enforce scope.

<Callout type="warning">
  **Fail-safe by design.** The connect check never holds the deferral — it runs asynchronously and only
  drops a player on a *confirmed* ban. No license key, relay down, or any API error simply lets the
  connect proceed. A slow or offline playerbase can never stall your server's join flow.
</Callout>

## Privacy

Raw identifiers never appear in shared reads — matching is done entirely on SHA-256 hashes. Your own
raw identifiers are kept only so *you* can lift your *own* records. Communities you share with see the
player's name and ban reason, never their identifiers.
