# Web Dispatcher (self-hosted bridge)

Beyond the in-game console, LACORE can feed a **browser dispatcher** so a dispatcher can work from a
second screen — or entirely off the game server. It does that through a **bridge you run
yourself**: LACORE pushes the CAD state to your bridge, the bridge serves it to the browsers, and
dispatcher actions come back to the game server through a token-gated endpoint.

![The self-hosted web dispatcher — your server, your bridge, the browser](/img/features/webdispatch-bridge.svg)

<Callout type="info">
  **The hosted portal was shut down in 4.2.0.** `setr lacore_webdispatch "true"` and the RP-WEB
  desktop on the LACORE website no longer work, and the licence key is not used for anything. The
  self-hosted bridge below is unaffected.
</Callout>

## How it works

```
FiveM (lacore)  ──POST /ingest (token)──▶  your bridge  ──WebSocket──▶  browser(s)
      ▲                                         │
      └──── POST /<resource>/action (token) ◀───┘
```

- **Outbound.** Every two seconds LACORE builds a snapshot — calls, units, the call queue, and the
  map images and named locations from `configs/cfg-livemap-sh.lua` — and posts it as JSON to
  `<lacore_bridge_url>/ingest`, with the token in the `X-Bridge-Token` header. It only sends when
  something changed. On an empty server it still pushes, just less often.
- **Inbound.** The resource answers on FiveM's own HTTP port at
  `http://<server>:<port>/<resourceName>/action`. A request needs the same `X-Bridge-Token`;
  without it the answer is `401`. `GET /health` is the only route that needs no token.
- The actions it accepts are `status`, `assign`, `resolve` and `create`. They run through the same
  functions the in-game MDT uses.

The snapshot goes to the address you set and nowhere else. LACORE itself receives nothing.

## Setting it up

<Steps>

### Run a bridge

Any service that accepts the `/ingest` push, serves the browsers and forwards actions to the
`/action` endpoint will do. Run it on a machine you control and put it behind **HTTPS**.

### Point LACORE at it

In your `server.cfg`:

```ini
set lacore_bridge_url   "https://dispatch.example.com"
set lacore_bridge_token "SHARED_SECRET"
```

Use a long random value for the token, and the same value on the bridge. Both convars have to be
set; with either one empty, nothing is sent.

### Restart the resource

The console prints `[webdispatch] self-hosted bridge enabled → <url>`. Without the convars it says
`[webdispatch] off`.

</Steps>

The module is switched on by `webdispatch = true` in `configs/cfg-features-sh.lua` (the default).

<Callout type="info">
  The reference bridge from the LACORE source (a Node service with a setup wizard and Discord login)
  is **not part of the resource download**. The resource only provides the two ends described above.
</Callout>

## Your own map images

![The same overlay loaded from url in-game and from webUrl in the web dispatcher](/img/dispatch/webdispatch-map-overlay.svg)

Map images from `configs/cfg-livemap-sh.lua` (see
[Your own map](/features/mdt-and-dispatch#your-own-map-overlays--named-locations)) travel with every
snapshot to the bridge. A browser outside the game cannot open `cfx-nui-` addresses, so give such an
overlay a public copy:

```lua
{
    id     = "postals",
    label  = "Postal map",
    url    = "https://cfx-nui-my-maps/maps/postals.png",  -- in-game console
    webUrl = "https://cdn.example.com/maps/postals.png",  -- web dispatcher
    from   = { x = -4140.0, y = -4200.0 },
    to     = { x =  4600.0, y =  8440.0 },
}
```

- An overlay whose `url` is already a public `https://` address needs no `webUrl`.
- Only `https://` images are sent. An overlay with just a `cfx-nui-` url is left out.
- `hideBaseTiles = true` is passed along as well.
- The image is loaded by each dispatcher's browser straight from the address you give, so pick a
  host you trust.

The named locations from `LiveMap.locations` ride along in the same snapshot.
`LiveMap.showLocations = false` hides them.

## Who may open it

That is the bridge's job. LACORE only checks the token on each request, so anyone the bridge lets
in can act on the live server. Put a login in front of the bridge and keep the token secret.

## What is audited

Every action a web dispatcher takes — status change, assignment, new call, disposition — is logged
in **Big Brother** as a web dispatch, with the name the bridge sends along for the dispatcher.

<Callout type="warning">
  The web dispatcher is **optional**. The in-game `/dispatch` console works fully on its own — the
  bridge is for teams that want an out-of-game dispatcher on a separate machine.
</Callout>
