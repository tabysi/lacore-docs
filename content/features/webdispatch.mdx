# Web Dispatcher (browser portal)

Beyond the in-game console, LACORE can feed a **browser dispatcher** so a dispatcher can work from a
second screen — or entirely off the game server.

There are two ways to get one. The **hosted portal** needs nothing but a licence key and a line in
your `server.cfg`; the **self-hosted bridge** is the original path and still works unchanged.

![The hosted web dispatcher — push, snapshot, actions ride back](/img/features/webdispatch.svg)

## The hosted portal (recommended)

Your server pushes its CAD state to LACORE every two seconds and reads the dispatcher's actions out
of the reply. Nothing listens on your server, and there is no second machine to run.

```
FiveM (lacore)  ──push every 2s──▶  lacore.netica.dev  ──▶  /server/<id> (browser)
      ▲                                                          │
      └────────── actions ride back in the reply ◀───────────────┘
```

<Steps>

### Set a licence key

The same key the dashboard uses. Generate it under **Dashboard → Licence keys** and put it in your
`server.cfg`:

```ini
set lacore_license_key "LACORE-XXXXX-XXXXX-XXXXX"
```

### Turn the web dispatcher on

It is **off by default** — call data leaves your server only once you say so:

```ini
setr lacore_webdispatch "true"
```

Restart the resource. The console prints `[webdispatch] hosted portal enabled`.

### Open it

Go to **Dashboard → Servers** and press **DISPATCH** on the server you want. That opens
`lacore.netica.dev/server/<id>` — the desktop with Dispatch, Map, Units and Radio.

</Steps>

### The map

The Map window draws the **game's own atlas tiles**, on the same calibration the in-game dispatch
console uses — a unit sits on the same street on both screens. Units are round and coloured by
status, calls are square, and clicking a call marker selects it in the Dispatch window. It opens
where the shift actually is rather than in the middle of the island; from there it is yours to pan
and zoom.

#### Your own map images

![The same overlay loaded from url in-game and from webUrl in the web dispatcher](/img/dispatch/webdispatch-map-overlay.svg)

Map images from `configs/cfg-livemap-sh.lua` (see
[Your own map](/features/mdt-and-dispatch#your-own-map-overlays--named-locations)) show on the
web dispatcher's map too, each with an on/off button under the map. A browser outside the game
cannot open `cfx-nui-` addresses, so give such an overlay a public copy:

```lua
{
    id     = "postals",
    label  = "Postal map",
    url    = "https://cfx-nui-my-maps/maps/postals.png",  -- in-game console
    webUrl = "https://cdn.example.com/maps/postals.png",  -- web dispatcher
    from   = { x = -4140.0, y = -4200.0 },
    to     = { x =  4600.0, y =  8440.0 },
}
```

- An overlay whose `url` is already a public `https://` address needs no `webUrl`.
- Only `https://` images are shown. An overlay with just a `cfx-nui-` url is left out.
- `hideBaseTiles = true` hides the atlas tiles in the web dispatcher as well.
- The image is loaded by each dispatcher's browser straight from the address you give, so pick a
  host you trust.

#### Named locations

![Named locations from cfg-livemap-sh.lua on the RP-WEB map](/img/dispatch/webdispatch-map-locations.svg)

The named locations from `LiveMap.locations` show on the web dispatcher's map as well, with the
same outlines and names as the in-game console. There is nothing extra to set: they come along
with every snapshot. `LiveMap.showLocations = false` hides them on both.

### Taking 911 / 311 calls

![Answering a 911 call from the web dispatcher](/img/dispatch/webdispatch-911.svg)

A dispatcher on the page can **take calls**, not only watch the queue:

- **Answer** a queued call (the desktop's queue has a button per call; the console's F1 / ANSWER
  takes the oldest). The call panel shows the caller, the trace countdown when
  [caller trace](/features/mdt-and-dispatch#caller-trace-911--311) is on, and the transcript.
- **Text only.** A browser has no in-game voice. The caller is told *"text only — answer with
  /callsay"* and every line they type lands in the transcript; you answer in the panel.
- **Hold / Resume**, **notes** (they go into the incident), and **End call** with *Create incident*
  ticked: the incident is created with the caller's location, exactly as from the in-game console,
  and the panel shows its number.
- **You count as a dispatcher.** While a dispatcher with the *dispatch* role has the page open, a
  911 call queues instead of becoming an auto-incident (`CallCenter.AutoIncident`), and the
  `/911` chat command is redirected to the phone as usual. Close the page and your call goes back
  to the queue for the next dispatcher — or ends, if nobody is left.

Viewers (the *view* role) see the queue but cannot answer. The self-hosted bridge does not carry
call sessions yet.

### What the page tells you

The portal never pretends to be live when it is not. It shows one of five states, decided by how old
the last snapshot is and what your account is allowed to do:

| State | What it means |
| --- | --- |
| **LIVE** | A snapshot arrived in the last ten seconds. Everything works. |
| **STALE** | Nothing for more than ten seconds. The windows dim, actions are held. |
| **OFFLINE** | Nothing for more than a minute. You are looking at the last state that arrived. |
| **READ ONLY** | You may look at everything and change nothing — the acting controls are gone, not greyed out. Refused server-side too, not just hidden. |
| **NO ACCESS** | You are signed in, but no role of yours grants dispatch here (or none has been granted to anybody). |

### Who may open it

Two ways in, and the second one is how you give a seat to somebody who is not on your dashboard:

1. **You**, and anyone on your dashboard team with the *servers* scope. Always, no Discord needed.
2. **A Discord role you name**, per server, in `configs/cfg-server-sv.lua`:

```lua
WebDispatchAccess = {
    dispatch = { "Staff", "Dispatch" },  -- may act: status, assign, create, close
    view     = { "Member" },             -- may watch, cannot act
}
```

Both lists are **empty by default**, which means nobody but you. The names come from
`DiscordAuth.roles` — the same table the in-game role checks use, so a role ID is written once.

The check runs **on your server**, with your own bot token. The portal only ever asks *"may this
Discord id dispatch?"* and gets back yes, read-only or no; your token, your guild and the roles
themselves never leave the machine. Anyone whose roles cannot be read — not in the guild, Discord
unreachable, no token configured — is refused rather than let through.

<Callout type="info">
  Because the answer comes from the game server, the first visit shows a short **"checking your
  access"** screen while the question rides along with the next snapshot, and a server that is
  offline cannot let anybody new in. Verdicts are remembered for five minutes.
</Callout>

## The self-hosted bridge

If you would rather run the whole thing yourself, LACORE still pushes to your own Node bridge and
accepts actions back through a token-gated endpoint.

```ini
set lacore_bridge_url   "https://dispatch.example.com"
set lacore_bridge_token "SHARED_SECRET"
```

The bridge broadcasts over WebSocket to your web app and relays dispatcher actions back into FiveM.
Both paths can run at the same time. Your map images (`webUrl`, see
[Your own map images](#your-own-map-images)) reach the bridge's web app the same way; rebuild the
app into the bridge (`cd web && npm run build:web`) after updating LACORE.

<Callout type="info">
  Because either portal accepts actions that affect the live server, keep `lacore_bridge_token`
  secret and expose the bridge over HTTPS only.
</Callout>

## What is audited

Every action a web dispatcher takes — status change, assignment, new call, disposition — runs through
the same functions the in-game MDT uses and is logged in **Big Brother** with the dispatcher's
Discord identity, marked as source `web`.

<Callout type="warning">
  The web dispatcher is **optional**. The in-game `/dispatch` console works fully on its own — the
  portal is for teams that want an out-of-game dispatcher on a separate machine.
</Callout>
