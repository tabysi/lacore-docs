# Framework Bridge

LACORE runs standalone with its own identity layer, but it can also **bridge to an existing
framework** so jobs and identity come from ESX, QBCore or QBox.

## Auto-detection

At load, the bridge (`modules/bridge/`) detects the active framework and exposes a uniform API:

| Function | Returns |
| --- | --- |
| `Bridge.GetJob(src)` | The player's job. |
| `Bridge.GetName(src)` | The player's character name. |
| `Bridge.GetIdentifier(src)` | A stable identifier. |
| `Bridge.IsLeo(src)` / `Bridge.IsEms(src)` | Duty checks. |
| `Bridge.Notify(src, msg)` | Framework-native notification. |

## Job → department mapping

Map your framework's job names to LACORE departments in `configs/cfg-bridge-sh.lua`:

```lua
Bridge.jobMap = {
  ['police']    = { dept = 'lapd', job = 'Law Enforcement' },
  ['sheriff']   = { dept = 'lasd', job = 'Law Enforcement' },
  ['ambulance'] = { dept = 'ems',  job = 'AMR' },   -- EMS/Fire in-game job string
  -- ...
}

Bridge.autoDuty = false  -- optionally auto-set duty from the framework job
```

A framework job that maps to an agency counts as **duty authorisation** — so an ESX/QB officer can go
on duty without also holding a LACORE Discord duty role. See
[Frameworks & Scripts](/frameworks-scripts) for the full compatibility list.

## Framework characters as the character source

On a framework server you don't want players filling out LACORE's `/char` on top of the identity they
already have. With `Bridge.useFrameworkCharacters = true` (the default), LACORE mirrors each player's
framework character on load and uses it everywhere — the MDT/CAD person lookup, `/profile`, and the
on-screen name. Multicharacter setups work out of the box: LACORE keeps one character per framework
character and re-syncs on every switch.

### ESX

| Pulled from ESX | Source |
| --- | --- |
| Name (first + last), date of birth, sex, height, phone number, job | `users` row for the current identifier |
| Registered vehicles (plates in the CAD query) | `owned_vehicles` for that owner |
| MDT licences | `user_licenses`, mapped in `Licenses.map` |

### QBCore & QBox

| Pulled from QB / QBox | Source |
| --- | --- |
| Name (first + last), date of birth, gender, phone number, job | `charinfo` of the loaded player |
| Registered vehicles (plates in the CAD query) | `player_vehicles` for that `citizenid` |
| MDT licences | `metadata.licences`, mapped in `Licenses.qb` |

Identity comes from the **loaded player object**, not from a database read, so a fork that renamed a
column still imports correctly. QB has no height on the character, so that field stays empty in LACORE.

<Callout type="warning">
  While the framework drives the character, its **identity is read-only in LACORE** (name / DOB / sex /
  height / phone / job) — the framework stays the single source of truth. Records, notes and
  relationships stay editable in LACORE. **oxmysql** is needed for the vehicle half (the identity
  import works without it). Set `Bridge.useFrameworkCharacters = false` to keep LACORE's own `/char`
  identity even while the framework still handles jobs.
</Callout>

<Callout type="info">
  The CAD person and plate queries fall back to the framework's own tables, so a character who has
  never connected since the import — or a car bought in the framework's shop and not yet mirrored —
  still shows up when an officer runs the search.
</Callout>

## Anticheat interop

The bridge marks legitimate framework events so LACORE's event-honeypot anticheat never flags them
(`Bridge.IsFrameworkEvent`).

<Callout type="info">
  No framework? LACORE uses its own multi-character identity — nothing else to configure.
</Callout>
